## 1. Overview

### 1.1 Product summary
UDVASITO is a free, bilingual (English / Bangla) blood-donor network for Bangladesh, starting in Chattogram. A family posts **one request** (form, Bangla voice, or pasted text). **Deterministic rules** match it to compatible, eligible, nearby donors who are notified in waves; **on-duty volunteers** see it at once and their number is shown to the family if no donor accepts within 30 seconds. A donor's number is shared **only after the donor accepts**. AI helps only with messy input (understanding free text and voice transcripts, rephrasing approved FAQ answers, polishing share text) — always after code has removed personal details, and always confirmed by a person. Platelet requests for dengue patients are a featured flow.

### 1.2 Problem (summary — evidence in `vision.md` §2)
Families still find donors by calling around and posting in scattered Facebook/WhatsApp groups; lists are stale; availability is unknown; volunteers duplicate effort; rare groups and dengue platelet needs are hardest to fill. The gap is **coordination**, not willingness.

### 1.3 The core loop (what judges see working)
1. Requester posts (≤ 60 s) → request live immediately.
2. On-duty volunteers of the area notified at once; first donor wave ≤ 60 s.
3. No donor accepted in 30 s → requester sees an on-duty volunteer's number.
4. Donor taps "I can help" → first *units + 1* acceptors confirmed → numbers exchanged (or "your donor will call you").
5. "Still coming?" checks; standby promoted if a donor goes silent.
6. 24 h later → "Did the donation happen?" → donor confirms → cooldown starts.

## 2. Goals and metrics

### 2.1 Goals (from `vision.md` §4)

| ID | Goal | Target | Window |
|---|---|---|---|
| G1 | Speed | (a) First donor wave sent ≤ **60 s** after publish; (b) median publish → first donor acceptance ≤ **15 min** for "Now" requests in the pilot area | (a) always; (b) by T0 + 60 days |
| G2 | Real impact | ≥ **25** requests with a **donor-confirmed** donation; full funnel on the dashboard | by T0 + 60 days |
| G3 | Participation | ≥ **300** real donors with verified phones before judging day (stretch 400); ≥ 500 by T0 + 60 days, all 8 groups; ≥ 70 % of active donors confirmed availability in the last 90 days | judging day / T0 + 60 days |
| G4 | Accessibility & reach | All core flows in English and Bangla; WCAG 2.2 AA on web; first screen usable ≤ 3 s on a mid-range Android over throttled 3G; ≥ 4 of 5 non-technical testers post a request unaided in ≤ 60 s | by judging day |
| G5 | Trust & safety | 0 donor numbers shown without consent; 0 phone numbers and no labelled names / addresses / diagnoses sent to the AI provider; 100 % of AI-filled fields confirmed by a person; every sensitive admin/volunteer action audited | always |

`T0` = judging day / public launch (target 2026-12-08).

### 2.2 Metric definitions (the backend computes these from recorded events — no separate counters)

| Metric | Definition |
|---|---|
| Time to first wave | `first_notification_sent_at − request_published_at` |
| Time to first acceptance | `first_donor_accepted_at − request_published_at`; median over requests with urgency "Now", place inside the pilot district, excluding practice-area requests |
| Volunteer shown rate | Share of requests where a volunteer's number was shown (V09) |
| Funnel | `published` → `donors_notified` → `alert_opened` → `donor_accepted` → `contact_shared` → `reported_by_requester` → `confirmed_by_donor` |
| Confirmation response rate | Requests with any answer to "Did it happen?" ÷ requests with `contact_shared` |
| Verified donors | Donor profiles live with a verified phone, excluding practice accounts |
| Availability freshness | Active donors whose availability was confirmed or changed in the last 90 days ÷ active donors |
| AI share | AI calls today ÷ provider free daily limit, per model |

**Events the system must record** (with timestamp, actor role, request ID, never with phone numbers): `request_published`, `request_updated`, `request_closed{reason}`, `wave_sent{n, size}`, `notification_sent`, `notification_opened`, `volunteer_notified`, `volunteer_shown`, `volunteer_claimed`, `donor_accepted`, `donor_declined{reason}`, `donor_confirmed`, `donor_standby`, `donor_withdrew`, `still_coming_asked`, `still_coming_answered`, `donor_not_responding_marked`, `contact_shared{mode: mutual|donor_calls}`, `donation_reported_by_requester`, `donation_confirmed_by_donor`, `report_filed{reason}`, `account_frozen`, `ai_call{feature, model, ok|fail|quota}`.

### 2.3 Judging acceptance test
Judges see the **live production platform**, not a mock-up or a slide demo (vision principle 10). Nothing shown is staged: every number is measured from real use, every button works.

**Part 1 — the real platform (about 2 minutes).** On `udvasito.com` and the installed Android app: the admin dashboard with **real pilot numbers** (live donors by blood group, requests, confirmed donations, volunteer coverage, time to first donor), real closed requests with their outcomes (anonymised), the audit log and the AI log. A judge may install the app or open the web app on their own phone and, if they wish and are eligible, register as a real donor.

**Part 2 — hands-on, in the practice area (under 3 minutes, on an Android phone *and* in a web browser, on venue Wi-Fi or mobile data).** The practice area is the same live system — real push, real AI, real Telegram, real phone calls — limited to practice accounts so a test request never wakes real donors (F-912):
1. A judge signs in with a practice ID + PIN on their own phone (or uses a team phone) and posts a request by Bangla voice → fields appear marked "AI suggested" → judge confirms → live.
2. A team phone signed in as an on-duty practice volunteer is alerted; after 30 s the judge sees the volunteer's number — and **Call really rings that phone**.
3. A team phone signed in as a practice donor receives the push → taps "I can help" → confirmed.
4. Both sides see each other's real number and the safety card; Call and WhatsApp connect.
5. The admin dashboard shows the request in the **practice** funnel, separate from the real numbers.

A recorded video of the same flow is kept **only** as a backup if the venue network fails.

## 5. Business rules and default settings

All numbers below are **defaults**, stored as settings (§5.10) and never hard-coded in logic. Rules marked 🩺 are medical-adjacent and must be reviewed by the medical reviewer (OQ-01) **before public launch**; until then the app shows them as "general guidance — the blood bank decides".

### 5.1 Donor eligibility 🩺
| Rule | Default | Source / reason |
|---|---|---|
| Age | 18–65 years (from date of birth) | A Bangladeshi medical journal lists 18–65 years, minimum 50 kg, haemoglobin ≥ 12.5 g/dL, and intervals of 3 months (men) / 4 months (women); WHO also gives 18–65 and ≥ 50 kg. 18 is also the account minimum (AI-provider terms) |
| Weight | ≥ 50 kg — self-declared checkbox | Same sources |
| Haemoglobin, blood pressure, infections | **Not checked by the app** — the blood bank screens | Not medical advice |
| Whole-blood interval | Men: 90 days; women, other, prefer not to say: 120 days | Bangladeshi guidance above (conservative value for non-male) |
| Platelet → platelet interval | 14 days | UK guidance: minimum 2 weeks between platelet procedures — conservative compared with some other countries |
| Platelet → whole blood | 14 days | Conservative; reviewer to confirm |
| Whole blood → platelets | Same as the whole-blood interval | Conservative; reviewer to confirm |
| Self-declared checklist at opt-in and at "I can help" | "I feel well today; I weigh at least 50 kg; I have not donated in the interval shown" | Rules decide; no AI |
| Gender field | Male / Female / Other / Prefer not to say — used **only** to pick the interval (OQ-14) | Minimisation |

### 5.2 Blood-group compatibility 🩺
**Whole blood (red-cell compatibility, used only in the last wave — see below):**

| Patient needs | Exact match (waves 1–2) | Also compatible (final wave, labelled "compatible — hospital will cross-match") |
|---|---|---|
| O− | O− | — |
| O+ | O+ | O− |
| A− | A− | O− |
| A+ | A+ | A−, O+, O− |
| B− | B− | O− |
| B+ | B+ | B−, O+, O− |
| AB− | AB− | A−, B−, O− |
| AB+ | AB+ | A+, A−, B+, B−, O+, O−, AB− |

- **Platelets:** exact ABO and Rh match only (default; reviewer may widen).
- **"Any group (replacement donor)":** every eligible donor matches; donors are told "any group — the blood bank will exchange your donation for the patient's blood".
- **"Not sure":** no donor alerts; volunteers alerted; requester asked to confirm with the ward.
- Whether to include compatible groups at all is a setting (S-11) — default **on in the final wave only**.

### 5.3 Matching and ranking (deterministic)
1. **Filter:** donor profile live, phone verified, not a practice account (unless practice request), available (not paused / not "not available"), eligible today (§5.1), group rule (§5.2), platelet opt-in for platelet requests, not blocked by/blocking the requester, not already notified for this request, within daily alert cap (S-20) and outside quiet hours unless the request is "Now" and the donor opted in to urgent alerts, "verified requests only" respected, travel range respected.
2. **Rank by place:** same thana as the hospital → neighbouring thanas (centre points within S-32 km) → same district → same division → wider.
3. **Tie-breakers (in order):** exact group before compatible; most recently active; fewer alerts received in the last 7 days (spreads load, protects rare-group donors); lower no-show count (S-37).
4. Take the next *wave size* donors from this ranked list.

### 5.4 Waves, volunteers and timers

| Step | Default |
|---|---|
| Wave 1 sent | ≤ 60 s after publish; size S-08a |
| On-duty volunteers in the area alerted | Same moment as wave 1 |
| Volunteer number shown to requester | If no donor accepted within S-13 (30 s); up to S-14 (2) volunteers, least-busy rotation |
| Next wave | After S-09 if confirmed units < units needed; size reduced by the number of wave-1 donors who opened but haven't answered (they're still deciding) |
| Final wave | Wave S-10 (3); includes compatible groups if S-11 on |
| Escalation | After final wave interval with no confirmed donor and no volunteer claim → all on-duty volunteers in district + admins |
| No volunteer on duty | Requester sees the super-admin's 24/7 fallback number (OQ-06, stored as a setting so a backup number can be added later) and the blood-bank list |

### 5.5 Confirmation, standby and no-show
- First **units + 1** acceptors confirmed (S-12); others standby, auto-promoted on withdrawal, "can't make it", "donor not responding", or silent "Still coming?".
- "Still coming?" at S-15 after confirmation and S-15c before needed-by; answer window S-16; silence → standby confirmed **in addition** (first donor kept unless they decline).
- No-show count increases when a confirmed donor is marked "not responding" or stays silent and the donation is later confirmed by someone else; affects ranking only (S-37), visible to admins, never public.

### 5.6 Request lifecycle states
`draft (on device)` → `live` → `covered` (confirmed units ≥ units needed; donors still notified? **no** — waves stop) → `closed` with reason: `fulfilled`, `not_needed`, `expired` (auto at needed-by + S-17), `removed_by_moderator`. A request can go `covered → live` if a confirmed donor withdraws and no standby exists. Requester can reopen within 24 h of closing.

### 5.7 Donor response states (per request)
`notified` → `opened` → `accepted` → `confirmed` | `standby` → `still_coming_yes` / `withdrew` / `not_responding` → outcome `donated_confirmed_by_donor` / `did_not_donate`. Or `declined{reason}`.

### 5.8 Limits and abuse thresholds
| Limit | Default |
|---|---|
| Open requests — unverified phone | 1 |
| Open requests — verified phone | 2 |
| Requests per account per month | 5 (volunteers posting on behalf: 20) |

| Freeze triggers | "Asked for money" report → account frozen; confirmed donor's "fake request" report → reveals on that request frozen |

### 5.9 Data retention
| Data | Retention |

## 6. AI features and guardrails

### 6.1 AI feature table

| Feature | Uses AI for | Input sent (after redaction) | Output | Human step | Without AI |
|---|---|---|---|---|---|
| F-206 Intake (typed / pasted / voice transcript) | Extract fields from messy English, Bangla, Banglish | Redacted text only | Blood group, units, whole blood/platelets, hospital name, area, needed-by, urgency | Requester reviews every "AI suggested" field and taps Post | Manual form; text kept |
| F-208 Duplicate hint (Should) | "Probably the same request?" | Two redacted request summaries (group, hospital, area, time) | Yes / no + reason | Requester or volunteer decides | Rules-only warning |
| F-604 FAQ assistant (Should) | Choose and rephrase approved FAQ entries; translate | The question (users warned not to include personal details; code redaction applied) + approved FAQ text | Answer citing the FAQ entry, or the fixed "ask a doctor" reply | Reader | Searchable FAQ list |
| F-1005 Appeal text (Should) | Polish a short bilingual appeal | Group, units, hospital, area, needed-by | Short text | Requester edits before sharing | Fixed template |
| F-908 Weekly summary (Should) | Plain-language summary | Aggregated numbers only | Paragraphs for admins | Admin reads | Numbers only |

**Not AI (by design):** matching, ranking, eligibility, compatibility, cooldown, limits, flags, slip verification, anything that decides who is contacted.

### 6.2 Redaction rules (run by code before every AI call)
1. Remove phone numbers (Bangladeshi formats with/without +88, spaces, dashes, Bangla digits) — extracted separately by code when needed (e.g. contact in a pasted post).
2. Remove the text after labels: রোগী, রোগীর নাম, নাম, Patient, Name, Mr., Mrs., জনাব, বেগম — up to the next comma/line break.
3. Remove known diagnosis/condition words from a maintained list (e.g. cancer, ক্যান্সার, dialysis, ডায়ালাইসিস, thalassaemia, থ্যালাসেমিয়া, surgery, অপারেশন, HIV) — the request does not need them.
4. Remove email addresses and national-ID-like numbers.
5. Log the **redacted** input and the output (S-36) for review; never log the original.
6. Automated tests cover each rule with English, Bangla and Banglish examples (NFR-02).

### 6.3 Quota plan (free tier as of Oct–Nov 2026: Flash-Lite ≈ 500 requests/day, Flash ≈ 20/day — re-checked in Step 5)
- **Flash-Lite** for every AI feature. Priority when quota is short: intake > duplicate hint > assistant > appeal text > weekly summary.
- At 80 % of the daily limit, the assistant and appeal text switch to their non-AI fallbacks automatically; intake continues until 100 %.
- Common assistant answers are cached.
- **Flash** reserved for nothing in v1 (kept as an emergency fallback model setting).

### 6.4 Responsible-AI commitments (shown on the About page and in the judging walkthrough)
1. AI never decides who is contacted — rules do, and they are visible.
2. AI suggestions are always labelled and confirmed by a person.
3. Code removes phone numbers, names and diagnoses before any AI call; users are told on the consent screen.
4. No AI medical advice; health questions go to doctors and blood banks.
5. 18+ only.
6. Every AI feature can be switched off instantly; the app works without AI.
7. AI inputs (redacted) and outputs are logged for 30 days for review.
